# Standalone Firefox local viewing investigation

On 2026-10-14 the user reported browser room access working but the broadcast never loading, while in-app viewing worked. The exact historical browser/settings were not confirmed; Windows' registered default browser is Firefox157.0.1. This investigation reproduced a matching failure with the real native synthetic publisher and a fresh installed-Firefox profile. It did not inspect or modify the user's normal profile.

Observed failing boundary: room join200, playback grant200, WHEP OPTIONS204 and SDP POST201; H.264/Opus capabilities and accepted SDP; zero delivered video dimensions, ICE failure and retry. Edge155.0.4283.45 played the same real source at720p and1080p. Codec/encoding initialization and room authorization did not fail in this reproduction.

Controlled comparisons used disposable profiles and stopped their services afterward. A temporary loopback TCP listener, test-only candidate preferences, and the pinned MediaMTX1.21.2 reference reader did not restore Firefox delivery. The documented upstream DTLS regression was fixed in1.19.1 and is not evidence for downgrading this1.21.2 deployment. Candidate classes and connection-state traces were kept separate from browser playback measurements.

Changing only the media bind/advertised address to this PC's Ethernet IPv4 address restored normal ICE checking/connection and actual1280×720 video with the original player and default Firefox media/privacy preferences. This establishes a working routing/configuration remedy on this PC. It does not prove that all Firefox versions/platforms reject loopback, nor isolate which OS/Firefox/network-interface behavior causes the underlying limitation. The machine also has a VPN adapter; no adapter or VPN was disabled, so its causal role is unproven.

The implemented fix is explicit `Start-Local.ps1 -MediaInterface Ethernet`, selecting exactly one preferred assigned unicast IPv4 address. Defaults remain loopback-only. Signaling, room HTTP, private authentication callback, API and metrics stay on localhost, while authenticated DTLS media is reachable on the chosen network interface. No firewall/router/browser settings or streaming codecs changed. Public hosting is a separate mode.

`MediaInterfaceChecks.ps1` covers private defaults, exact interface selection versus a VPN/IPv6/deprecated address, invalid addresses and ambiguity. `Test-FirefoxViewing.ps1` tests installed Firefox with a disposable profile, real synthetic capture, both requested output resolutions, independent decode progress, nonblank numeric pixel summaries, Opus packets and fullscreen return. Numeric evidence goes to `.artifacts/firefox-viewing/`; no personal capture recording is saved.

A test-probe assumption also failed: Firefox's `getVideoPlaybackQuality().totalVideoFrames` remained0 despite720p video and Playing status. `requestVideoFrameCallback` likewise produced no observations in this headless run, even after media attachment and with the video visible. The probe therefore records presented frames as unavailable, while independently requiring progressing inbound RTP decode counters and nonblank pixels. Neither zero counter is treated as a measured0FPS or as proof of rendering performance.

Verified Firefox157.0.1 results:720p had127 decoded frames and31 additional frames between samples approximately1second apart, pixel-luminance variance384.48,248 Opus packets and positive audio energy;1080p had253 decoded frames and60 additional frames, variance429.98,257 Opus packets and positive audio energy. Both ICE/peer connections were connected, sound selection and fullscreen return passed, and all owned test services stopped. The source was the small synthetic GDI window upscaled to the requested output; this is not a full-source1080 quality or sustained FPS result.

These are short same-PC media smoke tests. Sustained Firefox1080p60 gameplay, cross-device/network performance, real Discord exclusion, calibrated audiovisual offset and existing review blockers remain separate pending gates. Earlier ten-minute Edge evidence retains its original loopback topology and is not relabelled as a Firefox or Ethernet result.
