# Synthetic source and clock method

The original GDI fixture's ordinary 16 ms window timer measured approximately 39 actual paints/s. A high-resolution waitable timer/QPC scheduler brought its requested and measured paint cadence near 60. This did not imply Windows Graphics Capture accepted 60 distinct updates: the long run exposed approximately 51 accepted captures/s while encoding stayed near 60. The source's GDI drawing is not GPU presentation, and its 1264×721 client image is upscaled by the 1080p encoder. Preserve that result rather than calling it full-source 1080p gameplay acceptance.

`native/timing-source/TimingSource.cpp` is a separate native D3D11 comparison source. It draws 1920×1080 client pixels using GPU rectangles and a flip swap chain with maximum frame latency one, while targeting 60 updates/s using the same QPC scheduler. It retains the same moving-band/color pattern, clock-strip layout and application audio bursts as the timing fixture. No second media encoder or new streaming architecture is introduced. It builds to `.artifacts/timing-source/Debug/CaptureFixture.exe`; the existing explicitly selected development-fixture audio profile applies.

A 32-bit low Unix-millisecond code sits between two magenta sync blocks. The receiver discovers its scaled position, decodes the black/white cells, and subtracts it from the browser's Windows wall clock once per second. On the **same PC** this measures drawing/painting to browser callback, including capture, encoding, transport and decode queues. It does not measure physical screen photons. A browser on another device needs measured clock offset/uncertainty or another timing method; ICE RTT cannot replace that measurement. Low clock bits wrap after about 49.7 days, handled by unsigned modular subtraction; decoded ages above two seconds are rejected as invalid rather than treated as real latency. Windows/browser millisecond clock quantization and callback/readback overhead add uncertainty. Report valid/missing sample counts and analysis time; do not hide rejected codes.

The short 15-second GDI calibration decoded all 15 clock samples and measured 204 ms p95 to callback, 59.73 presented FPS, a 32.3 ms maximum callback gap, and 100% of complete five-second intervals at ≥55 FPS. These results justified running the longer experiment; they were not sustained acceptance.

The audio source emits a quiet 997 Hz, 50 ms burst once per second through waveOut. The visual flash uses the device's reported waveform sample position. Device reporting/paint/presentation do not establish delivered audiovisual synchronization by themselves. The viewer records numeric WebAudio spectral peaks with 8192-point FFT and no waveform file; that FFT window has timing uncertainty and is not currently a calibrated A/V-offset analyzer. Delivered A/V offset remains pending. The short controlled run received 997 Hz at -51.43 dB, while separate 1801 Hz native and 2753 Hz browser playback sources appeared at -96.44/-103.91 dB or lower. This demonstrates a measured synthetic exclusion margin, not actual Discord exclusion or an absolute silence guarantee.

The acceptance harness records rVFC presented-frame intervals and gaps, native acquisition/compositor/encoded/sent counters, separate OBS render and video-output skipped-frame counters (the same APIs used by pinned OBS's statistics window), native CPU, device-wide NVIDIA utilization and room media/NIC observations. Device-wide GPU usage may include other applications. Numeric source measurements and reports are stored; no real gameplay, desktop picture or audio waveform is saved.
