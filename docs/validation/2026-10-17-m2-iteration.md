Deep portable extraction paths no longer lengthen Chromium's data directory. Existing profiles are left alone, the native session supplies the room cookie, and user/System-only profile ACLs remain. Initialization failures identify the profile folder and give write-access/runtime guidance.

## Playback investigation

The user reports Firefox needing three reconnects, but had not tested an already-established broadcast. The in-app error was a separate WebView2 data-directory failure, before media negotiation. Its reported portable root is 165 characters; the former `.runtime/webview/<64-character hash>/EBWebView` suffix brings it close to the Windows legacy path limit before Chromium creates deeper files. Short, user-local profile placement removes that installation-dependent failure condition. A live WebView2 run using that exact nested portable root passed after the change.

The 404 message previously suggested an expired grant. Actual host behavior rejects absent/invalid/expired grants with 401/403. MediaMTX 1.21.2 maps its `PathNoStreamAvailableError` to WHEP POST 404, before creating the reader's SDP answer; this is distinct from codec decoding or ICE connectivity. The room exposes a reservation before the native engine is prepared and media tracks become available. Watching during that interval, or during a restart, is a plausible explanation, but it is **not a confirmed diagnosis of the user's three-attempt case**. The previous warning-only media logs did not retain evidence establishing that case. See [pinned upstream reader code](https://github.com/bluenviron/mediamtx/blob/v1.21.2/internal/servers/webrtc/session.go#L459-L479).

The iteration leaves the retry count, delays and ICE deadline unchanged. It corrects error categorization and adds the last four per-card connection results: OPTIONS/POST status, failure stage, per-stage/total timing, gathering/ICE/connection states, local candidate type counts and estimated grant time remaining at POST. Successful results remain alongside preceding failures. No SDP, token, invitation, media path or network address is retained. The device-clock grant estimate is explicitly labeled and never controls authorization.

Open the arrow **Connection diagnostics** control after a problem. Browser viewers can download the report; **Show report** provides selectable JSON for copying in the in-app viewer, whose download restriction remains intact. To narrow down a recurrence, retain that report immediately after success/failure, note Firefox version, whether broadcaster/viewer/host share a PC and network, whether the stream was already running for a minute, and the approximate broadcast-start time. Compare same-origin Firefox and WebView2 at the same time. If POST is 404, correlate with publisher start/restart/stop and media readiness; if HTTP succeeds but ICE fails, inspect UDP/interface/NAT/relay evidence instead.

## Architecture answers

### OBS without a system installation

The portable package contains its own OBS 32.2.2 runtime and the application-owned `jk-obs` extension. `OwnedObsProcess` starts `.runtime/obs/bin/64bit/obs64.exe` with `--portable --multi`, the bundled JKiller profile/scene collection, updater disabled and minimized startup. The app controls that process through its private named pipe and owns its lifetime. Windows Graphics Capture/D3D11 supplies video; the extension selects application or explicit system-output audio; OBS encodes H.264/Opus and publishes over WHIP. The personal OBS installation and profiles are not required or used. Browser-only viewers need neither OBS nor the desktop application. WebView2/VC++ prerequisites remain as documented in the portable guide.

### Independent 720p viewing of a 1080p broadcast

Current architecture: one H.264/Opus encoding pipeline and one generated `/main` media path per broadcaster. MediaMTX forwards that encoded media to each WHEP receiver. A smaller video element scales the picture after reception; it does not reduce the received resolution/bitrate or decoding work. Existing broadcaster settings can lower the shared output for everyone. There is no per-viewer quality ladder, transcoding worker, rendition grant or quality-switch protocol.

Feasible future approaches:

| Approach | Required project changes | Resource tradeoff |
|---|---|---|
| Shared server-side renditions | Add a supervised FFmpeg/GStreamer worker per publication, decode/scale/encode a 720p variant once and share it among viewers. Provide a protected worker ingest/output path; current RTSP is disabled and auth accepts WebRTC only. Extend the hard-coded `/main` path/proxy/grant allowlists, variant discovery/authorization, stop/restart/revocation lifecycle, monitoring, and player rendition switching. Preserve the original while variants warm up. | Broadcaster still uploads one source. Server adds decode/scale and each lower-quality encode, CPU or GPU/VRAM, worker memory, buffering/latency and operations. More publishers and qualities multiply that compute; more viewers mainly multiply network delivery, not encodes. |
| Broadcaster-generated variants | Extend the owned OBS/plugin pipeline to produce/upload multiple encodings and add equivalent rendition routing, grants and viewer switching. This is not implemented simulcast support in the current application. | More broadcaster encoding/GPU sessions and upload bandwidth; less server transcoding compute. |

For this architecture, shared server-side transcoding is the natural option if preserving one broadcaster upload matters. MediaMTX documents using [FFmpeg/GStreamer for re-encoding](https://mediamtx.org/docs/features/remuxing-reencoding-compression). It is not a viewer-dropdown-only change. Each worker/rendition would be shared, not created per viewer; automatic adaptation would additionally require bandwidth estimation and switching policy, whereas manual selection could come first.

Illustrative network arithmetic, not a quality or hardware benchmark: a 6 Mbps rendition transfers approximately 2.7 decimal GB per viewer-hour; a 3 Mbps rendition transfers 1.35 GB, before audio/protocol overhead. Server egress is the sum of viewers' selected bitrates. Sending both from the broadcaster would instead require roughly 9 Mbps upload. Actual compute capacity, latency and hosting fees require benchmarking the chosen FPS/encoder/hardware and applying the hosting provider's rates; this iteration does not measure or price them. No quality selection was implemented.
