# Firefox H.264 negotiation at 1080p60

2026-10-20, follow-up to `1f7e0a8` on `codex/browser-broadcast-1080p60`. Preserve the earlier [browser quality report](2026-10-20-browser-1080p60.md) and its workload limits.

## Cause and correction

The owner's Firefox screen publication still encoded 1280x720 at roughly 30 fps despite the updated capture and sender targets. The live host served the updated website. The supplied diagnostics showed H.264 `profile-level-id=42e01f`, Level 3.1. MediaMTX 1.21.2 advertises that receive level, and Firefox applies its frame-size/macroblock-rate limits to its encoder.

The host now advertises Level 4.2 (`42e02a` or `42002a`) in successful WHIP SDP answers for the pinned receiver's matching baseline/constrained-baseline codecs. The offer and answer must both explicitly allow level asymmetry and packetization mode 1. The adapter requires a matching, unambiguous single active video section and receive-only answer; it leaves explicit extra limits and unrelated negotiations untouched. Level 4.2 accommodates 1080p60. This changes receiver capability signaling; the offer, WHEP answers, media pipeline and browser encoder selection remain unchanged.

The pinned MediaMTX receive path accepts/routes the higher-level H.264 RTP without transcoding. Revalidate this compatibility when changing the pinned server. Sources: [MediaMTX incoming codecs](https://github.com/bluenviron/mediamtx/blob/v1.21.2/internal/protocols/webrtc/inbound_track.go), [receive-to-stream routing](https://github.com/bluenviron/mediamtx/blob/v1.21.2/internal/protocols/webrtc/to_stream.go), and [RFC 6184 section 8.2.2](https://www.rfc-editor.org/rfc/rfc6184#section-8.2.2).

## Measured evidence

- A fresh-profile Firefox 158.0.1 synthetic H.264 peer test reproduced **1280x720 at 29.9581 encoded fps** with the original Level 3.1 answer. Keeping the offer unchanged and advertising Level 4.2 in the receiver answer produced **1920x1080 at 59.8922 encoded fps**, decoded at 1920x1080 by the receiving Firefox.
- A separate real production-web/host/MediaMTX 1.21.2/Firefox publisher/Firefox viewer run passed at **1920x1080**, approximately **60.06 encoded fps** and **59.84 decoded fps**, after a five-second warmup and over a five-second sample. The publisher retained one encoding with `maxBitrate=12000000`, `maxFramerate=60` and `scaleResolutionDownBy=1`. The viewer used the unchanged WHEP answer. Stop sharing removed the stream and closed viewer peers.
- These tests used disposable Firefox 158.0.1 profiles, official OpenH264 2.6.0, a synthetic moving bar, loopback website/signaling and same-PC Ethernet media on separate test ports. The installed Firefox profile, running user host, MediaMTX and tunnel were not stopped or reconfigured. Initial fixture attempts without an initialized codec or with loopback-only Firefox media did not establish a working stream; the final test used the verified codec and reachable Ethernet route.
- Twenty HTTP-boundary regressions cover both eligible profiles and unchanged WHEP/non-H.264, asymmetric-level restrictions, packetization restrictions, higher levels, mismatched profiles/MIDs/payloads, rejected sections, duplicate parameters/attributes, explicit lower limits and another media section reusing a payload number. The two positive cases failed before implementation and passed afterward. Original offer bytes, HTTP status, content type and resource Location are checked.

Raw diagnostics and disposable fixture files remain ignored under `.artifacts/firefox-*`. No live invitation, ICE credential, private address or raw user SDP is included in Git.

## Limits and using the correction

The test substitutes a fixed 1920x1080 canvas for the display chooser. Its test-only `applyConstraints` shim checks the exact production 1080p60 request because Firefox canvas tracks reject the display-capture constraints; it does not establish real `getDisplayMedia()` behavior. Encoding, transport, decoding, room authorization, publication and cleanup remain real. This short test does not establish real-screen capture, captured audio, sustained/high-motion or external-network performance, hardware encoder identity or CPU/GPU/game impact. The 12 Mbps setting remains a ceiling, not constant measured output. Remaining M3 acceptance gates are unchanged.

Rebuild and restart the host to load this host-side correction. For an active temporary tunnel, stop it when ready and run `Start-TemporaryTunnel.ps1` again with the intended media interface; use its newly printed invitation and start a new browser publication. Updating or refreshing only the website cannot replace an already running host DLL. No Firefox preference changes are required.
