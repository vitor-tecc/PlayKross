**Goal:** Deliver a Windows broadcaster with application-only audio, one working browser viewer, in-app viewing, honest diagnostics, and reproducible setup and validation instructions.

**2026-10-14 user scope amendment:** “you can skip that audio part for now to be honest.” Continue M1 as an explicitly video-only milestone. A small native OBS extension binds audio to an exact process identity, with narrowly scoped engine instrumentation for actual capture and encoding measurements.

## Global constraints

- Windows 11 is the initial broadcasting target; SDR video is the initial color mode.
- All global desktop/system audio sources and audio-input-device sources are disabled.
- There is no microphone picker, permission request, capture path, mixing route, or microphone control.
- Discord, the broadcaster/viewing application's process tree, general browsers, and shared browser-host applications are ineligible audio sources in the first release.
- Source loss pauses or blanks video and mutes its associated audio until the user explicitly confirms a replacement.
- Slider range: 1-25 Mbps in 0.5 Mbps increments.
- 480p means 854x480; 720p means 1280x720; 1080p means 1920x1080. FPS is 30 or 60. Preset bitrates are 2/3, 4/6, and 8/15 Mbps respectively.
- Requested resolution/FPS/bitrate remain distinct from configured engine state and observed delivery.
- No silent CPU fallback is allowed. Offer explicitly selected software H.264 at 720p30 if NVENC initialization fails.
- Missing measurements are null with a reason, never zero or a copied requested setting.
- Network RTT is not end-to-end video latency.
- Initial configured upload budget: 175 Mbps. Reserve 20% above estimated media bitrate inside that budget; this is provisional, not measured capacity.
- Keep application-owned runtime, secrets, logs, captures, and dependency build trees out of Git. Never alter the user's personal OBS installation or profile.
- Do not contact friends or record private desktop/audio samples without the user's authorization. Real external validation may require user participation.
- One main rendition only in this plan. Shared previews, eight-viewer scaling, multiple broadcasters, grid/focus, annotations, resize, cursor controls, and zoom are later milestone work.
- Use Superpowers TDD for behavior, systematic debugging for failures, code review for milestone acceptance, and verification-before-completion before success claims.

## Review focus

1. A source process exits and its PID or window title is reused: capture must not attach to the replacement (Tasks 2-4).
2. Start, Stop, settings changes, and disconnect arrive concurrently: only one publication may exist and obsolete operations cannot resurrect it (Tasks 5 and 9).
3. A nickname, invite, or stream path contains unusual Unicode, markup, or traversal syntax: display safely and preserve authorization boundaries (Tasks 6-8).
4. A playback session completes its handshake after the user leaves: dispose the late connection and delete its WHEP resource (Task 8).
5. Statistics reset, disappear, or use a different clock after reconnect: report unavailable/reset values instead of negative rates or fabricated latency (Tasks 10-11).

## Versions, build prerequisites, and implementation decisions

Read-only planning verified OBS 32.2.2 as the official stable release and MediaMTX 1.21.2 as the official stable media-server release. The Microsoft .NET 10 release index listed SDK 10.0.401/runtime 10.0.12. The first dependency task pins those candidates and verifies downloaded hashes. If a relevant security/compatibility update is available at execution, update the manifest deliberately and record the reason; do not use floating `latest` URLs at runtime.

OBS Windows x64 ZIP SHA-256: `4d6e40e3ab155f56b30de517380566a206d74b63cdf5ad49aa596924768f97e1`. Obtain the MediaMTX archive hash from that release's published checksums and .NET hash from Microsoft's release index. Resolve frontend/.NET package versions once during Task 1 and commit their lockfiles. Do not invent unverified archive hashes.

Use application-owned, removable dependencies under `.tools/` and `.runtime/`. A .NET SDK is required for build; an existing dotnet runtime is insufficient. The native module/instrumented engine requires the C++ build environment and Windows SDK supported by the pinned OBS build presets. Detect installed Visual Studio Build Tools through `vswhere`; report required components rather than silently installing a system toolchain. Native code requires C++20 and the Windows process-loopback activation headers.

OBS's standard application-audio source calls `ms_find_window` on initialization/reconnection. Strict title matching alone does not bind a source to a process lifetime. Therefore all eligible application audio goes through `jk_process_audio`, a native source using `ActivateAudioInterfaceAsync` in process-tree inclusion mode. Hold an open process handle, verify its creation time and image path, and never reacquire a replacement. The process itself and its child tree are the capture boundary; approved source classification must account for that tree. Unknown shared hosts stay silent.

Native audio uses a bounded 200 ms PCM queue, discarding the oldest PCM on overload and reporting the discard. It never buffers indefinitely or changes to endpoint loopback. Capture and output clocks use a documented monotonic conversion; no wall-clock timestamp subtraction for encoding delay.

Control sessions use 256-bit random secrets, 12-hour expiry, and server-side storage of their hashes. Browser credentials use HttpOnly cookies; desktop credentials use Windows DPAPI. Publishing/reading grants are separate opaque 256-bit capabilities, scoped to a stream path/action, with a 60-second handshake validity. Expiry limits new handshakes; established sessions are stopped explicitly by the host when membership/ownership is revoked. OBS reconnect obtains a new grant through the desktop controller and restarts, rather than retaining an expired token indefinitely.

Local default ports: room API/UI 5000, private media signaling 8889, private MediaMTX API 9997, metrics 9998, private media-auth callback 5001, and media UDP 8189. All HTTP listeners bind loopback in the local profile. Public/LAN profiles expose only the documented room/signaling proxy and media socket, with administrative listeners remaining private.
