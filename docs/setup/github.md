## Automatic Windows releases

Once `.github/workflows/release.yml` reaches `main`, every update pushed or merged to `main` starts **Windows release**. It prepares the pinned .NET SDK/OBS downloads on a clean Windows runner, installs locked browser dependencies, runs integrated CodeOnly checks, builds the modified OBS capture library and packages the desktop app. PRs run the same build/package gate with read-only permissions but cannot publish a release. Every main update runs independently; newer updates do not cancel an older build.

After successful verification and packaging, an isolated publishing job validates the ZIP against its checksum/manifest, uploads all three files to a draft and publishes it as a prerelease. Find downloads at [Releases](https://github.com/vitor-tecc/PlayKross/releases). Automatic builds use `ci-<GitHub-run-id>-<12-character-commit>` tags and filenames, not milestone acceptance numbers. They do not replace an existing stable release's Latest designation. Pick the newest successful main build by commit/run date; build completion order can differ from push order.

For a manual build, open **Actions → Windows release → Run workflow**, select `main` and run it. To recover a failed build/upload, use **Re-run failed jobs** or **Re-run all jobs** on that run. The same run retains its version; an incomplete draft can be repaired, while an already published release is left unchanged. A newly dispatched run gets a new version. Failed uploads leave a draft visible to maintainers rather than exposing a partial download. Feature-branch manual runs can package but cannot publish.

The publishing job uses GitHub's automatic `GITHUB_TOKEN` with `contents: write`; other jobs remain read-only and no personal access token or new repository secret is required. Repository/organization Actions policy and tag rules must permit the checked-in workflow and release-tag creation. Actions is currently enabled in the repository; if policy blocks a run, inspect its Actions log. Build artifacts are retained for seven days; published release assets remain until deliberately removed. No automatic release deletion is configured.

GitHub also restricts creating/updating a release for a commit whose `.github/workflows` files differ from the current default branch: that needs workflow-write authorization, which `GITHUB_TOKEN` cannot receive. An older build or delayed rerun can therefore fail publication after a newer main update changes workflows. Its verified ZIP remains in the run's temporary artifact. Normally use the newer successful release or dispatch a fresh main build; if the exact older release is needed, a maintainer must publish/recover it with workflow-authorized credentials. The workflow reports this failure rather than tagging a different commit or installing a broader token. See [GitHub's release API permission note](https://docs.github.com/en/rest/releases/releases#create-a-release).

Repository changes still follow verification, commit, feature-branch push and PR review. GitHub can build only changes pushed to it. This automation does not watch uncommitted local files, auto-merge PRs or deploy the server. Server operators clone the repository and follow [Windows setup](windows.md) and [internet hosting](internet.md).

Automated prereleases do not close the pending M3 hardware/media acceptance. Release notes retain that limit. The ZIP is the desktop broadcaster/viewer with its clean OBS runtime; .NET is bundled, while WebView2 Evergreen/Visual C++ runtime may be needed. Real AMD/NVIDIA capture, audible audio, external networks and game impact require separate live checks. The workflow neither captures the maintainer's screen nor starts their services.

For a fresh clone, follow [Windows setup](windows.md). Source still uses the existing `JKiller` project/assembly names to avoid unnecessary protocol, profile and build-path changes; the product name is PlayKross.
